\## 7. BAM 5.6 — Duplicate Incident Detection and Idempotency



\### Objective



The objective of BAM 5.6 was to test whether the incident-reporting system could recognize repeated incidents and avoid creating duplicate Jira tickets.



\### Reviewing the Python Implementation



Before running the test, I inspected the `report\_incident()` function inside `incident.py`.



The function accepts:



```python

report\_incident(

&#x20;   agent,

&#x20;   severity,

&#x20;   message,

&#x20;   incident\_id,

&#x20;   evidence='',

&#x20;   recommendation=''

)

```



I found that it checks an SQLite database for the incident ID before creating a new Jira issue.



The relevant SQL query is:



```sql

SELECT jira\_key, jira\_url, slack\_sent

FROM incidents

WHERE incident\_id=?

```



I also checked where the incident database was configured.



The script defines:



```python

STATE\_DB = Path(

&#x20;   os.getenv('INCIDENT\_STATE\_DB', 'data/incident\_state.db')

)

```



The default SQLite database location is:



`/opt/balerica-bank/data/incident\_state.db`



This path applies unless the `INCIDENT\_STATE\_DB` environment variable overrides it.



\### Test Procedure



I called `report\_incident()` twice using the exact same incident ID:



`BAM-DUP-JMK-001`



Both calls used a simulated ERROR incident with the same message and supporting information.



The purpose was to verify that the first call creates a ticket while the second recognizes that the incident already exists.



\### Actual Test Results



\*\*Run 1\*\*



```text

Incident ID: BAM-DUP-JMK-001

Jira key: BAI-6

Jira created: True

Slack status: sent

```



\*\*Run 2\*\*



```text

Incident ID: BAM-DUP-JMK-001

Jira key: BAI-6

Jira created: False

Slack status: already\_sent

```



\*\*Final Verification\*\*



```text

BAM 5.6 RESULTS

Same Jira key: True

Duplicate prevented: True

PASS: Incident idempotency verified

```



\### Results Table



| Verification | First Run | Second Run |

|---|---|---|

| Incident ID | BAM-DUP-JMK-001 | BAM-DUP-JMK-001 |

| Jira issue | BAI-6 | BAI-6 |

| New Jira ticket | Yes | No |

| Slack status | sent | already\_sent |

| Duplicate created | No | No |



\### Where the Incident ID Is Stored



The incident ID is stored in a local SQLite database.



The database maintains a record of the incident ID, its associated Jira key and URL, and whether the Slack notification was sent.



Before creating a new Jira issue, `report\_incident()` checks whether the incident ID already exists in the database.



When I submitted the same incident ID a second time, the script retrieved the existing Jira issue information rather than creating another ticket.



Since the Slack alert had already been sent, the second run also avoided sending a duplicate notification.



This implementation demonstrates sequential idempotency in the lab. It isn't intended to provide distributed locking or guarantee duplicate prevention across multiple concurrent agents.



\### What I Learned



This exercise helped me understand why idempotency matters in monitoring and incident-management systems.



An application might report the same failure several times, especially when automated checks run repeatedly.



Without duplicate handling, those repeated reports could create multiple Jira tickets and flood Slack with unnecessary alerts.



By reusing the existing Jira issue and recording notification status, the script helps reduce duplicate work and alert fatigue.



I also learned that SQLite can be used to maintain lightweight application state, even when the main purpose of the application is to communicate with external services.
